## Context

当前目录包含项目约定和 OpenSpec 配置，但没有模型、训练代码、数据读取或评估实现。项目目标是把 YOLO 系列方法作为可读的学习材料，同时能在共同数据条件下比较实验结果。第一阶段以 YOLOv1 跑通训练、验证和推理纵向流程；基线使用 `yolo_final_20k`，采用 YOLO TXT，类别顺序为 person/car，train/val 分别为 18,000/2,000 张。

## Goals / Non-Goals

**Goals:**

- 实现一条结构清楚的 YOLOv1 路径，从模型、版本训练配方到共同数据集上的评估和推理。
- 把可复用的执行流程与版本专属的网络、损失、标签分配、增强和后处理分开。
- 保存每次运行实际使用的配置和评价条件，使后续版本与自定义方法能在同一数据集上复现实验。
- 让版本文档解释论文思想、张量流、代码位置和实现差异。

**Non-Goals:**

- 在本变更中实现 YOLOv1 以外的全部 YOLO 版本，或声称复现各论文公开的基准分数。
- 预建注册表、插件机制、复杂继承体系或大型通用配置框架。
- 自动下载数据或权重、修改用户数据、启动长时间训练，或实现部署后端。
- 假设用户数据的具体目录、类别顺序或划分规则，直到检查实际数据。

## Decisions

### 1. 以版本目录承载方法特有逻辑，共享训练执行骨架

模型、标签分配、损失和推理后处理放在 `x_yolo/models/yolov1/` 等版本目录内。共享训练器只负责编排批次、优化步骤、检查点和日志；它通过清楚的 Python 调用边界使用版本实现，不把版本差异藏进大量条件分支。

**Alternatives considered:** 把每个版本实现写成独立训练脚本会重复数据和运行流程；用通用模型注册系统则会过早引入抽象，降低学习可读性。

### 2. 使用共同数据集和评估约定，保留版本训练配方

所有对比实验使用同一份用户数据、类别映射和固定划分。每个方法单独保存来源可追溯的训练配方；共同训练入口读取这些配置并记录实际值。复用或适配论文配方时，应注明针对用户数据所作的调整。结果表示“共同数据集上的各自配方表现”，不得称为论文原始基准结果。

**Alternatives considered:** 强行固定所有版本的优化器和增强参数会偏离论文方法；逐论文使用不同数据集则无法形成直接横向对照。

### 3. 在评估边界显式规范检测结果

各版本可保留自己的原生输出和解码方式；评估入口将结果显式转换为统一的 `xyxy` 像素坐标、类别 ID 和置信度，再计算共同指标。数据集评估与 PyTorch/部署后端数值对比是两种不同任务，分别实现和记录。

**Alternatives considered:** 把所有后处理塞入模型 `forward` 会增加导出和理解难度；复用后端一致性对比脚本也不能替代数据集检测指标。

### 4. 为实验保存可追溯快照

每次运行单独输出实际配置快照、数据集划分标识、类别映射、输入预处理、评价阈值、随机种子、代码版本、环境信息和指标。模型权重及运行结果保存在被忽略的输出目录，不纳入源码提交。

**Alternatives considered:** 只依赖终端日志难以比较和复现；引入外部实验跟踪服务会增加依赖和服务副作用，当前没有必要。

### 5. 数据读取从一个明确的数据集适配器起步

第一版支持 `yolo_final_20k` 的 YOLO TXT 标注：每张图对应一个文本标注文件，逐行读取类别 ID 与归一化边界框（class_id, x_center, y_center, width, height）。训练和验证图片/标签各 18,000/2,000 对，类别顺序为 person、car。原数据集 YAML 的根路径指向其他机器，项目单独提供数据配置和命令行根路径参数，不修改原 YAML。实测所有 20,000 个标签文件均可解析，图像/标签同 stem 配对完整，标签值在合法范围内。

**Alternatives considered:** 第一阶段同时支持多种格式会扩大范围；隐式自动转换会增加数据损坏和类别错配风险。

### 6. YOLOv1 网格冲突显式使用单目标策略

论文版 YOLOv1 每个 7×7 网格单元只有一组类别概率，因此同一单元出现多个目标时无法完整表示。对当前数据按归一化中心映射到 7×7 网格统计，train 有 16,408/18,000 张、val 有 1,817/2,000 张存在冲突；冲突涉及的额外标注分别为 128,892 和 13,726。首版 target builder 在每个格子保留面积最大的目标，稳定规则处理并列面积，同时统计被忽略目标数；评估仍使用原始全部标注。文档和每次运行元数据必须报告该适配，不能把结果称为完整监督下的 YOLOv1。

**Alternatives considered:** 静默丢弃碰撞目标会误导结果；改成更大的输出网格或切图推理会改变模型结构或测试协议，不属于这条忠实的 YOLOv1 基线。

### 7. 新方法按真实差异扩展

新增论文版本使用独立版本目录和版本说明。自定义方法按实际修改的模型组件、损失、标签分配或训练策略组织，并保留可读的配置差异。只有多个实现证明同一段逻辑稳定共享后才提取公共代码。

**Alternatives considered:** 把每个消融项都做成插件会让初学者难以追踪调用路径；把不同算法强行合并到一个版本类中则会模糊方法边界。

## Risks / Trade-offs

- [用户数据与论文数据分布不同，论文配方的效果可能下降] → 报告数据来源与配方调整，区分共同数据集上的实验结果和论文原始基准结果。
- [YOLOv1 网格冲突使大量训练目标不能获得独立监督] → 采用明确的最大面积目标策略，保存碰撞统计，并在评估和文档中说明其限制。
- [数据集原 YAML 的路径和注释统计与当前环境可能不一致] → 使用项目单独配置和现场扫描结果，不覆盖原文件或把旧注释当作事实。
- [版本间输入预处理或后处理不同会影响比较] → 在版本适配边界记录预处理和阈值，并在结果报告中展示这些条件。
- [YOLOv1 细节可能与论文或后续工程实现不完全一致] → 版本文档逐项标明来源和差异，不使用“严格复现”表述，除非证据支持。
- [当前仓库没有确定深度学习框架或依赖管理方式] → 设计/实现前确认本机环境和用户偏好，优先选择轻量且易解释的方案。

## Migration Plan

这是一个从空代码骨架开始的新增能力，没有现有模型接口需要迁移。按纵向流程逐步新增配置、数据适配器、YOLOv1 实现、共享训练和评估入口、版本说明及小规模运行方式。用户数据和权重由用户放置在仓库外或本地忽略目录；若实现过程中发现数据语义不匹配，停止运行并修正显式配置，不覆盖源数据。

## Open Questions

- 首版训练参数沿用论文配方时，需明确对当前数据集的输入增强和有效 batch size 适配；不下载 ImageNet 预训练权重。
